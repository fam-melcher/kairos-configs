# 0016 — Correcting ADR 0014's one-shot mechanism (sentinel files)

- Status: Accepted
- Date: 2026-07-25

## Context

[ADR 0014](0014-one-shot-node-render.md) decided that a fragment renders
a node-local artifact exactly once by deleting its own `/oem/<name>.yaml`
file as its last command, reasoning that "Kairos only executes stages it
finds in `/oem` at boot; a fragment that removes itself... simply is not
there to run again next boot."

That premise is false for an installed node. Verified directly on a live
node (`node-cf1b52c0`, k8s-prod): after install, `/oem` contains exactly
one file, `90_custom.yaml` — Kairos's auto-installer merges every
fragment staged during install into this single file; the individual
`/oem/11-cluster.yaml`, `/oem/12-tls-san.yaml`, `/oem/13-join.yaml`,
`/oem/15-kube-vip.yaml`, `/oem/16-argocd.yaml` never exist under those
names again. Every `rm -f /oem/<name>.yaml` ADR 0014 introduced is
therefore a no-op against a file that was never at that path, and the
containing stage — still sitting inside `90_custom.yaml` — re-executes
in full on every subsequent boot, exactly the behavior ADR 0014 set out
to stop.

Confirmed impact, by grepping the merged file on a node that had already
survived multiple reboots: the "Render kube-vip manifest" and "Render
ArgoCD manifest" stages (and, by the same mechanism, the tls-san and
join-target renderers) were still present and re-running. All four write
into real persistent storage — `/etc/rancher/k3s/config.yaml.d/` and
`/var/lib/rancher/k3s/server/manifests/` are backed by `/dev/sda5`, a
real ext4 partition (`mount` output), not Kairos's ephemeral `/etc`
overlay — so every boot silently reverted whatever the live cluster (an
operator, or ArgoCD itself) had changed at those paths since install.
This is not a theoretical gap: it is what undid a live fix to ArgoCD's
self-management bootstrap mid-investigation, immediately after a reboot.

## Problem

Given that individual `/oem/*.yaml` fragment files do not persist as
separate files past install time, what mechanism actually makes a stage
run exactly once, for the rest of the node's life?

## Considered Alternatives

1. **Status quo (ADR 0014's `rm -f /oem/<name>.yaml`)** — does not work,
   per the above. Rejected — this ADR exists because of it.
2. **Sentinel/marker file** — the exact alternative ADR 0014 itself
   considered and rejected ("adds a second moving part... two ways to
   reset it inconsistently"). That objection assumed the chosen
   alternative worked; it does not, so the trade-off is now "one moving
   part that does nothing" vs. "one moving part that works." Chosen.
3. **Self-editing `/oem/90_custom.yaml`** — a stage could `yq eval -i
   'del(...)'` its own entry out of the merged file directly, closer in
   spirit to ADR 0014's original intent (the fragment's presence in
   `/oem` remains the only signal). Rejected: fragile (matching and
   removing one's own stage entry by name/index from a file every other
   fragment is also concurrently rendered from is a much larger blast
   radius for a mistake — a bad match deletes or corrupts unrelated
   stages), and gains nothing a sentinel file doesn't already provide
   more simply.

## Decision

Guard each affected stage with an `if:` condition (already a supported
cloud-config stage field — `configs/base/00-base.yaml` already uses one
for the Hyper-V serial-getty check) testing for a sentinel file, and
`touch` that same sentinel as the stage's last command instead of `rm -f
/oem/<name>.yaml`:

```yaml
- name: "Render kube-vip manifest"
  if: '[ ! -f /oem/.rendered-15-kube-vip ]'
  commands:
    - |
      ...
      touch /oem/.rendered-15-kube-vip
```

The sentinel lives in `/oem` itself — a real, separate ext4 partition
(`/dev/sda2`), not the ephemeral `/etc` overlay — so it is exactly as
persistent as ADR 0014 always assumed the fragment file's absence would
be. One dotfile per one-shot fragment, named after the fragment
(`.rendered-<fragment-basename>`), applied to:

- `configs/cluster/12-tls-san.yaml`
- `configs/cluster/13-join.yaml`
- `configs/cluster/15-kube-vip.yaml` (its "Render kube-vip manifest" step
  only — "Stage kube-vip manifest template" was already correctly
  idempotent-every-boot and untouched)
- `configs/roles/16-argocd.yaml` (its "Render ArgoCD manifest" step only,
  same reasoning)

`clusters/<name>/config/11-cluster.yaml` (generated by `iso/dispatch.sh`'s
`stage_cluster_values`) is deliberately **excluded** — see Rationale.

## Consequences

- `/etc/rancher/k3s/config.yaml.d/{10-env,20-join}.yaml` and
  `/var/lib/rancher/k3s/server/manifests/{kube-vip,argocd}.yaml` now
  actually render once, as ADR 0014 always intended: a live change made
  through the cluster's own tooling after install now genuinely survives
  a reboot.
- A node that is reinstalled gets a fresh `/oem` (a new partition, laid
  down by the installer), so its sentinels are gone too — the one-shot
  fragments render again exactly once, same as ADR 0014 promised.
- `iso/dispatch.sh`'s `stage_cluster_values` loses its (always-dead)
  "Cluster values one-shot cleanup" stage entirely rather than gaining a
  sentinel guard — see Rationale for why this one is different.
- Anyone adding a new render-from-`cluster.env` consumer must now ask
  "does this write to a real persistent path (`/etc/rancher`,
  `/var/lib/rancher`, `/usr/local`, `/oem`) or Kairos's ephemeral `/etc`
  overlay?" before choosing whether it needs this guard at all — get it
  wrong in the sentinel direction on an ephemeral path and the node
  breaks on its second boot (the sentinel skips the render, but nothing
  else recreates the ephemeral file the skip assumed still existed).

## Rationale

`cluster.env` itself (`11-cluster.yaml`'s output) lives at
`/etc/kairos-cluster/cluster.env` — under `/etc`, which `mount` confirms
is Kairos's ephemeral overlay (`upperdir=/run/overlay/etc/.overlay/upper`,
`/run` being tmpfs), reset from the read-only `sysroot` layer on every
boot. Applying this ADR's sentinel guard there would have been actively
wrong: after the first boot the sentinel would exist in `/oem` (real,
persistent) but `cluster.env` would not (wiped along with the rest of
`/etc`), and every downstream consumer `.`-sources it as their first
command — the node would break on its second boot, not its first.
Re-rendering the same frozen, install-time values into an ephemeral path
every boot is harmless (it always reproduces identical content) and is
in fact required for that path to exist at all; the actual protection
this whole ADR cares about — not clobbering a live, in-cluster change —
only applies to fragments rendering into real persistent storage, which
`11-cluster.yaml` does not do.
